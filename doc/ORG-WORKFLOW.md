# Org 工作流

这套工作流只有一条主要规则：

> 需要行动的内容放进 `tasks.org`，其他内容放进 `ideas.org`。

## 文件

`my/org-dir` 指向的目录包含：

```text
tasks.org     活动任务
ideas.org     想法和普通笔记
archive.org   已完成内容
init.org      可选的 beorg 配置
```

`tasks.org` 和 `ideas.org` 都是平铺结构。每个条目都是一级标题。不要增加
`* Tasks` 或 `* Inbox` 之类的容器标题。

这种结构与 beorg 的捕获方式一致，也省掉了单独整理 inbox 的步骤。

启动只检查上述三个数据文件是否存在，不自动创建。已有 Dropbox 数据时先核对路径并
等待同步；全新使用时显式运行 `M-x my/gtd-initialize`，仅创建缺失文件。

## Capture

使用 `SPC a o c` 打开捕获菜单。

```text
t   在 tasks.org 中创建 TODO 条目
n   在 ideas.org 中创建普通标题
```

两个模板都会将新条目追加到文件末尾，不会询问标签、日期或目标文件。

## 日常视图

使用 `SPC a o o` 打开 Agenda，再选择：

| 按键 | 视图 | 内容 |
| --- | --- | --- |
| `d` | 今天 | 今天的日程、排期，以及到期和逾期事项 |
| `t` | 待办 | 没有排期、截止日期或活动时间戳的 `TODO` |
| `r` | 回顾 | 全部 `TODO`，不按排期、截止日期或活动时间戳过滤 |
| `w` | 等待 | 所有 `WAITING`，包括已安排跟进日期的事项 |
| `s` | 以后 | 所有 `SOMEDAY` |

“今天”不再附带整个任务池，默认也不提前展示未来截止事项（条目显式设置的提前提醒仍有效）。`SOMEDAY`、`DONE` 和
`CANCELLED` 不进入这个视图，即使条目还留有旧日期。没有状态的日历事件仍然显示。
未来安排可以用 Org 自带的周 Agenda（菜单 `a`）查看。

`WAITING` 平时在等待视图中回顾；为它设置 `SCHEDULED` 跟进日期或真实的
`DEADLINE` 后，会在对应日期进入“今天”，逾期未处理时继续提醒。

每天从 `t` 中选少量真正准备推进的任务，用 `SCHEDULED` 安排到今天。
只在确有截止要求时使用 `DEADLINE`，不要为了隐藏任务随便填日期。
每周回顾一次 `r`、`w`、`s`。`r` 包含未排期、未来安排和带旧日期的全部 `TODO`，
避免仅有过去活动时间戳的未完成任务被遗漏；这类时间戳不会像排期一样持续提醒。

## 状态

| 状态 | 含义 | 何时改变 |
| --- | --- | --- |
| `TODO` | 已经决定做，尚未完成 | 做完改为 `DONE`；需要别人推进时改为 `WAITING` |
| `WAITING` | 等待外部进展 | 有进展后改回 `TODO` 或直接 `DONE` |
| `SOMEDAY` | 可能会做，暂未承诺 | 决定推进时改为 `TODO`，同时检查旧日期 |
| `DONE` | 已完成 | 需要时归档 |
| `CANCELLED` | 已决定不做 | 需要时归档 |

进入 `WAITING` 时，在日志里写明等谁、等什么；需要主动跟进时安排日期。
改为 `SOMEDAY` 时检查原来的排期和截止日期，清理失效日期；仍有真实截止要求的
事项应继续作为承诺管理。重新激活时也要检查日期，避免旧日期立即产生逾期提醒。

Capture 仍然默认创建 `TODO`。只是一个念头时使用想法模板；已有行动描述但
尚未承诺时可以改为 `SOMEDAY`。不增加 `NEXT` 或新的整理层级。

桌面端按需记录状态：进入 `WAITING` 或 `CANCELLED` 时记录备注，离开 `WAITING`
时记录时间（目标状态要求备注时改记备注）；这些日志写入 `LOGBOOK`。
普通 `TODO → DONE` 转换写入 `CLOSED` 时间戳，
不会另加一条完成状态日志；普通 `TODO` 与 `SOMEDAY` 之间的转换也不记录。
重复任务完成后记录重复日志，并回到 `TODO`。
在 Org 条目中用 `SPC m T T` 改状态、`SPC m d s` 排期；Agenda 中也可以使用这两个入口。

## Refile

Refile 的作用是将条目移动到其他文件，不能把条目挂到另一个任务下面。

允许的目标只有：

- `tasks.org` 顶层
- `ideas.org` 顶层
- `archive.org` 顶层

三个设置共同保护平铺结构：

- `org-refile-use-outline-path` 为 `file`，因此可以选择文件根部。
- 三个文件都使用不会返回标题的正则表达式。
- Refile 时不能临时创建父标题。

除非同时补充平铺结构测试，否则不要简化这些设置。

## Archive

归档条目追加到 `archive.org` 末尾，并保持一级标题。`tasks.org`、`ideas.org` 和
`archive.org` 因此使用相同的平铺结构，不需要容器标题。

## 重复任务

使用普通 Org repeater：

```org
* TODO 查看工作邮箱 :work:
SCHEDULED: <2026-08-29 Sat .+1d>
```

完成后，Org 会计算下一个日期，并将条目恢复为 `TODO`。它在排期日期进入
“今天”，不会出现在未排期待办视图中。

## 标签

只预设 `personal` 和 `work` 两个标签，用来区分个人与工作任务。在标题上按
`C-c C-c` 可以选择标签。Capture 默认不询问标签；只有确实需要分类时再添加。

历史条目中例如 `health` 和 `learning` 的其他标签仍然是有效的 Org 语法，但不再作为
快速选择界面的预设项。除非产生稳定的查询需求，不要再扩充标签列表。

## beorg 契约

桌面 Emacs 和 beorg 必须在以下方面保持一致：

- TODO 与 DONE 状态
- 任务和想法的捕获目标
- 已启用的日志使用 `LOGBOOK` 抽屉
- 重复任务恢复状态
- 从任务视图排除的文件

两端的日志触发范围不同：beorg 默认还会记录已有条目进入完成状态的转换，
桌面端采用上面的按需规则。`LOGBOOK` 约定统一日志位置，不表示每种转换都产生相同记录。

上述五个视图是 Emacs 配置。beorg 继续使用现有的 Agenda 和按状态分组的 Tasks；
Emacs 的视图过滤不会同步到手机。手机上的状态含义采用同一套规则，具体视图仍需
在 App 中核对。

仓库中的 `beorg-init.sample.org` 只管理官方文档明确支持的 Scheme 设置。任务和
想法的捕获模板在 App 界面中创建。设置和检查方式见[配套软件](COMPANION-TOOLS.md)。

## 数据安全

不要同时在 Emacs 和 beorg 中编辑同一个文件。在手机上编辑前，先保存桌面 buffer。
如果 Dropbox 产生冲突副本，删除任何一份之前都要先比较两边内容。

Emacs 使用 lockfile 防止两个 Emacs 实例同时编辑同一文件。beorg 不识别
这种锁，所以它不能代替上述人工协调。本机 `backups/` 保留编号备份：最新 10 份和
最早 2 份。Dropbox 或 beorg 冲突时，先保留所有副本，再用本机备份辅助比较。
